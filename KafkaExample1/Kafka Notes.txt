------------------    ZooKepper  Notes   ---------------------------
What is ZooKeeper?
ZooKeeper is a distributed coordination service used by Kafka (before version 4.0) to store cluster metadata and help manage the Kafka cluster.

Think of ZooKeeper as:
👉 Kafka’s manager + coordinator + cluster brain
       Kafka brokers = workers
       ZooKeeper = supervisor

Why Kafka needed ZooKeeper (before KRaft)
ZooKeeper handled all critical cluster metadata that brokers could not coordinate themselves.
ZooKeeper kept track of:
        Which broker is alive?
        Which broker is the controller?
        Who is leader of each partition?
        What are ISR replicas?
        Topic metadata (topics, partitions, configs)
		
What ZooKeeper Does in Kafka (Important Functions):--
1. Broker Registration
When a Kafka broker starts, it registers itself with ZooKeeper.
ZooKeeper stores:
    Broker ID
    IP address
    Port
    Configs
So ZooKeeper always knows who is alive.

2. Controller Election
In Kafka cluster, one broker becomes controller.
Controller is responsible for:
    Leader election for partitions
    Assigning replicas
    Handling broker failures

ZooKeeper elects this controller.
If the controller broker crashes → ZooKeeper picks another one.

3. Leader Election for Partitions
For each partition, ZooKeeper decides:
    Which replica becomes leader
    Which replicas are followers
Leader handles all messages.
ZooKeeper ensures only one leader exists for each partition.

4. ISR Management (In-Sync Replicas)
Kafka replicas that are fully caught up = ISR.
ZooKeeper keeps track of:
    ISR list updates
    When a replica falls behind
    When a replica rejoins ISR
If the leader dies → ZooKeeper picks a new leader from ISR.

5. Metadata Storage
ZooKeeper stores cluster metadata:
    Topics
    Number of partitions
    Replication factor
    Access control lists
    Broker configuration overrides

Kafka brokers read/write this metadata using ZooKeeper.


------------------    Kafka Notes   ---------------------------
What is Apache Kafka?
Apache Kafka is a distributed event streaming platform used to build real-time data pipelines and streaming applications.
Think of Kafka as a high-performance messaging system that allows different applications to send, store, and receive messages (events) at massive scale.

------Core Concepts in Kafka------
1. Producer
         Application that sends messages to Kafka.
         Example: Payment service publishes "payment_success" event.
         
2. Consumer
         Application that reads messages from Kafka.
         Example: Notification service receives "payment_success" event and sends an SMS.

3. Topics
         Category or stream name where messages are stored.
         Example: "payments", "orders", "logs".

4. Partitions
         Each topic is split into multiple partitions for parallelism and scaling.
         Messages in a partition are always ordered.

5. Brokers
         A Kafka broker is a server.
         A Kafka cluster = multiple brokers working together.

6. Consumer Group
         A group of consumers that share the load of processing partitions.
         Kafka ensures each partition is read by only one consumer in a group.

7. Offset
         A unique number identifying each message inside a partition.
         Consumers track offset to know what they have read.
		 

---------   How Kafka Works (Simple Explanation)   ------------
Producers publish messages into topics
→ Kafka stores them in partitions.

Kafka stores data on disk (but very fast)
→ Uses sequential, append-only writes.

Consumers read at their own speed
→ Kafka doesn’t delete data immediately after reading.

Consumers track their own offsets
→ Allows reprocessing data if needed.

------------------------   Kafka Architecture — Deep Dive --------------------------
1️ Kafka Cluster:-
A Kafka cluster consists of:
    i.    Kafka Brokers (servers)
    ii.   ZooKeeper (older versions) or KRaft (new Kafka versions) for metadata and coordination
    iii.  Producers
    iv.   Consumers
    v.    Topics & Partitions
    vi.   Replication
    vii.  Offset Storage
    viii. Controllers

All these components together create a reliable event streaming system.

2️. Kafka Broker:- 
A broker is a single Kafka server.
Each broker stores a subset of partitions.
A cluster typically has 3, 5, or 7 brokers.
Each broker has a unique ID.
A broker stores data in topics, and each topic is split into multiple partitions.

3️. Topic and Partitions:-
✔ A Topic is a logical category
Example: orders, payments, inventory.

✔ A Topic is split into partitions
Example:
orders → 3 partitions
orders-0
orders-1
orders-2

✔ Why partitions?
    To scale horizontally.
    To achieve parallelism.
    To maintain ordering within each partition.

📌 Kafka guarantees ordering only per partition, not across the topic

4️. Partition Leaders & Followers:-
Each partition has:
🔹 One Leader
    Handles all reads/writes.
    Clients talk only to the leader.
	
🔹 Zero or More Followers
     Replicate data from the leader.
     Provide failover.

Example (replication factor = 3):

Partition 0:
  Leader → Broker 1
  Follower → Broker 2, Broker 3
  
5️. Replication (RF = Replication Factor):-
Used for fault tolerance.
If RF = 3:
    1 leader
    2 followers
    
Kafka ensures:
    Followers pull the log from leader.
    Followers replicate sequentially.
    Followers send acknowledgments.

If a leader dies:
    One of the in-sync followers becomes the new leader.

6️. ISR (In-Sync Replicas):-
ISR = Replicas that are fully synced with the leader.
Requirements:
    Follower must not be too far behind leader.
    Follower must send regular heartbeats.
Kafka promotes only ISR members to be leader.

7️. Kafka Controller (The Boss):-
The controller:
    Manages broker failures.
    Performs leader election.
    Manages partition assignments.
    Coordinates rebalancing.
	
Kafka uses:
🔸 ZooKeeper → in older versions
🔸 KRaft (Kafka Raft) → in new versions
to elect the controller.

8️. Log Storage (Kafka’s secret weapon):-
Kafka uses append-only logs.
Each partition is a log file:
    message0
    message1
    message2

Benefits:
    Very fast sequential disk writes
    OS page cache optimizations
    Zero-copy data transfer
Kafka stores messages as:
    Batch of messages
    Offset (long), Key (optional), Value, Timestamp, Header.

9️. Message Retention:-
Kafka does not delete messages immediately after consumption.
Retention types:
⏳ Time-based

Keep messages for 7 days.
🔢 Size-based

Keep 100 GB per partition.
🧹 Compaction

Keep only the latest value for each key.

10. Producer Internals:-
Producers choose:
✔ Partition
Using:
    Round-robin
    Sticky partitioning
    Key-based hashing (ensures ordering by key)
	
Acknowledgment level (acks setting):-
| acks | Meaning                    | Durability      |
| ---- | -------------------------- | --------------- |
| 0    | No wait                    | Fastest, unsafe |
| 1    | Leader ack                 | Good            |
| all  | Leader + ISR followers ack | Safest          |

Producer also manages:
    retry logic
    batching
    compression (snappy, gzip, lz4, zstd).
	
11. Consumer Internals:-
Consumers read from topics using pull mechanism:
    Kafka does NOT push messages.
    Consumers request specific batches from partitions.

Consumer Groups
    A consumer group is a cluster of consumers reading a topic.

Rules:
    Each partition is assigned to exactly one consumer in a group.
    Multiple groups can read the same data independently.
	
1️2. Offset Management:-
Offsets can be stored in:
✔ Kafka internal topic → __consumer_offsets (default)
✔ Manually in external DB (for custom behavior)

Consumers commit offsets:
    Automatically
    Manually
    Asynchronous commit
    Synchronous commit
	
1️3. Rebalancing:-
When consumer joins/leaves the group:
   Kafka reassigns partitions.
   Controlled by Group Coordinator & Consumer Coordinator.
   Uses rebalance protocols (Range, RoundRobin, Sticky).

Newer versions use:
   Incremental cooperative rebalance (very fast)
   Avoids complete rebalancing
   
1️4. KRaft (Kafka Raft Mode) — New Architecture:-
Kafka is removing ZooKeeper.
KRaft does:
   Metadata management
   Controller election
   Maintaining cluster state
   Log replication (Raft)

Benefits:
   Faster startup
   Less complexity
   Better HA
   Strong consistency  
   
1️5. End-to-End Flow Example:-
A producer publishes to topic orders:
   Producer finds metadata → gets partition leader
   Producer sends message to leader
   Leader appends to log
   Followers replicate
   Acks returned to producer

Consumer reads:
   Consumer pulls messages from leader
   Processes data
   Commits offset
   Rebalance if needed

--------------   Why ZooKeeper is not required anymore   -------------
Because Kafka learned to manage itself.

Earlier:    Kafka needed ZooKeeper to coordinate brokers.

Now:  Kafka has KRaft, which replaces ZooKeeper and handles all metadata inside Kafka itself.

So:
     No separate ZooKeeper cluster needed
     Faster startup
     Faster leader election
     Easier scaling
     One system to run, not two

If your using Below 3.6 version of kafka then Zookepper is required , it will act as manager and store the logs and elect the Controller , Leader , follower so on ..

First Run Zookepper :-

Wihtout Zookepper first time we need to --->
      Kafka uses an internal metadata log (not ZooKeeper)
      Each broker stores metadata in the log directories
      Before the first startup, Kafka needs:
      A cluster ID (UUID)
      The log directories to be formatted with this cluster ID

If you skip the formatting, Kafka will show errors like: No metadata log found Storage directory not formatted


Step 1: Generate a Cluster ID (random UUID)

        kafka-storage.bat format --cluster-id K8rGdLf8T8Wmy1RyNbQx1A --config config\server.properties

Then Start the kafka server directly (No ZooKepper is required here)
Command :-  kafka-server-start.bat C:\kafka_2.13-3.9.0\config\kraft\server.properties
